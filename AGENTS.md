This file provides guidance to coding agents working with code in this repository. Domain vocabulary lives in `CONTEXT.md`; architectural decisions live in `docs/adr/`.

## Architecture

The pipeline deliberately keeps ffmpeg dumb — no filter graphs, just raw frames piped to its stdin for encoding, and (in overlay mode, see below) raw frames piped from its stdout for decoding — audio analysis and rendering are done entirely in Python so they aren't constrained by what an ffmpeg filter graph can express:

1. **`audio.py`** decodes the full track with librosa up front and produces per-*video*-frame arrays (not per-audio-sample): smoothed log-spaced band energies, a smoothed overall-loudness (RMS) envelope for `Motion.rigid`/`Motion.pulse`, a precomputed flash brightness envelope (onset detection, decayed and combined via elementwise `max` so overlapping onsets don't blow out to solid white), and a precomputed flash color per frame (spectral centroid lerped between the active `Palette`'s `flash_primary_color` and `flash_secondary_color` — held constant at `flash_primary_color` when a palette has no secondary, which is how monochrome palettes fall out of the same lerp with no special case). `hop_length` is chosen as `sample_rate / fps` specifically so analysis-frame indices align 1:1 with output video frames with no resampling step. The RMS envelope is log-compressed with `20*log10` (amplitude-domain), not the `10*log10` used for the power-domain band energies, then percentile-normalized the same way — different compression constant, same normalization pattern.
2. **`render.py`** draws each frame in Cairo, along these independent axes:
   - **Subject** — what the Motion animates: a **`Shape`** or an **`Image`** (see "Image Subjects" below). `render_frame`'s `subject` parameter takes either.
   - **`Shape`** (`--shape` flag, default `face`): three complementary pairs, each tiling the bounding square exactly — `face`/`space` (an arbitrary quadrilateral, and the concave pentagon that is the square minus it), `face2`/`space2` (narrow right-hand column), `face3`/`space3` (scalene triangle along the top edge). The enum is an explicit allowlist, not generated from `nltl_values.shape_names()`: a new nltl-values shape is only added after it's been looked at under every Motion (a thin or triangular shape can self-intersect under `deform` amplitudes tuned for `face`). `test_every_shape_choice_exists_in_nltl_values` keeps the enum honest against the pinned version. Coordinates are not defined here: `_polygon_vertices` reads each shape's unit-square points from the pinned `nltl-values` package (`nltl_values.shape(shape.value)` — screen orientation, y-down, same as Cairo) and maps that unit square onto the centered bounding square. Change shapes in nltl-values and bump the tag in `pyproject.toml`; don't keep local copies. Both the shape's motion and the flash's position scale from the polygon's own centroid (shoelace formula, works for either shape regardless of convexity), not canvas center.
   - **`Motion`** comes from the resolved `Preset`'s `motion` field (see ADR 0002) — there is no `--motion` flag. `deform` (the default) distorts the perimeter per-band (arc-length-parametrized, so control points map to real distance traveled around the boundary regardless of how uneven the edges are — `deform_amplitude`), stroked outline, gradient-blob flash. `rigid` keeps the shape's plain proportions and instead uniformly scales the whole thing from its centroid, driven by the RMS envelope oscillating both directions around baseline (`scale_amplitude`, `scaled_polygon_points`) — solid flat fill instead of a stroke, and the flash becomes a smaller solid-filled concentric copy of the same shape (`draw_inner_shape`) rather than a radial gradient. `pulse` (see ADR 0001) is a constant-size, constant-shape, single-flat-color fill with no flash and no centroid-driven color blend at all — reactivity is entirely the fill's alpha, `preset.pulse_max_opacity * scale_envelope[i]`. `pulse` is also the only motion that inscribes the shape edge-to-edge in the frame's shorter dimension (`_PULSE_HALF_FRACTION = 0.5`, via `pulse_polygon_points`) rather than `deform`/`rigid`'s small centered `_BASE_HALF_FRACTION = 0.35` — `_polygon_vertices` takes an explicit `half_fraction` specifically so this doesn't leak into the other two. `deform_amplitude`/`scale_amplitude`/`pulse_max_opacity` are deliberately separate preset fields (not one field reinterpreted by mode) so a preset's numbers don't silently change meaning depending on an unrelated flag — and since `motion` itself is now also a preset field, each preset's amplitude numbers and its motion are pinned together permanently, not combined at the CLI. `split` cuts the plain shape along its bounding square's horizontal midline (`split_polygon_points`) and slides the top half left and the bottom half right by `split_amplitude * size * scale_envelope[i]` — stroked outline, no flash, like `pulse` deliberately minimal. Neither shape nor motion special-cases `space`'s concave reflex vertex — if a preset's amplitude ever produces visible self-intersection near that corner, that's the first place to look.
   - **`Layout`** (`--layout` flag, default `single`): `single` draws one shape centered in the canvas — `_layout_instances` returns the one `(size, offset)` pair, `size` taken as-is from the caller (by convention always `min(width, height)` — see `_frame_generator`/`_overlay_frame_generator`). `grid` draws a fixed 2x2 of four identical copies, all driven by the same per-frame band/flash/scale values (no spectral split per quadrant) — `_layout_instances` in this case *ignores* the caller's `size` and re-derives a quadrant-fit size from the canvas dimensions directly, since a quadrant's own space, not the single-shape basis size, is what should drive its scale. `render_frame` paints the background once (`_paint_background`) then calls `draw_shape_instance` once per `_layout_instances` entry — that split exists specifically so grid mode doesn't repaint over its own previous quadrants.
   - Color (background/outline/flash) is deliberately *not* a fourth axis on `Preset` — it lives on a separate `Palette` (see ADR 0003 and `palette.py`), passed into `render_frame`/`draw_shape_instance` alongside `Preset`, since a hex color carries no per-`Motion`-tuned semantics the way `deform_amplitude` etc. do.
3. **`postprocess.py`** applies grain and vignette as plain numpy ops on the rendered RGB buffer.
4. **`encode.py`** pipes frames to ffmpeg's stdin as raw RGB24 and drives a determinate Rich progress bar (frame count is known up front, unlike nltl-animate, which can't observe ffmpeg's internal progress). `render_video` itself is decoupled from how the ffmpeg command is built — callers pass a prebuilt `cmd`, either `build_ffmpeg_cmd` (audio-only: audio file muxed in, re-encoded to AAC) or `build_overlay_ffmpeg_cmd` (overlay mode: the source video's audio track stream-copied through unchanged, since it's the same bytes already used for analysis — no reason to pay for a second lossy encode).
5. **`cli.py`** has a non-obvious Click/Typer detail: `nltl-viz <audio>` (a bare positional argument) and `nltl-viz presets` (an explicit subcommand) must coexist. A plain Typer callback can't do this — Click's group-level argument parsing consumes a leading positional token before ever checking subcommand names. The fix is a custom `_DefaultCommandGroup(TyperGroup)` that overrides `resolve_command` to prepend the hidden `render` command when the first token isn't a known subcommand, combined with `context_settings={"ignore_unknown_options": True}` so the group's own parser doesn't reject subcommand-specific flags like `--preset` before dispatch happens. If you touch the CLI's argument/subcommand structure, re-verify all three invocation shapes (bare filename, flags-first, zero-args interactive, explicit `presets`) — each one broke independently while this was first built.

Presets and palettes each follow the same shape as nltl-animate's: a flat frozen dataclass of fields, a small hardcoded built-in dict, and an optional YAML config file (`presets:`/`palettes:` top-level keys) whose entries are checked first and fall back to the built-ins by name — `config.resolve_preset`/`config.resolve_palette` are the two lookup entry points, sharing a `_read_yaml` helper for the OSError/YAMLError-to-ValueError translation. `config.load()` additionally validates a YAML preset's `motion` field is one of `Motion`'s values (`deform`/`rigid`/`pulse`/`split`) at load time, same eagerness as its unknown-field check; `config.load_palettes()` has no equivalent extra validation since every `Palette` field is just a hex string or `None`. NLTL colors come from nltl-values' **`art.*` group only** — never `brand.*` or `web.*` (`art` is the group nltl-values maintains for image generation/animation, so it can diverge from the website brand without nltl-viz noticing). Backgrounds: `black` → `art.bg-dark`, `grey` → `art.bg-light`, `violet`/`teal` → `art.canvas`; accents are `art.primary`/`art.secondary`. The one local hex is `black`'s cool-grey outline `#D8D8D2`, which has no nltl-values equivalent. `test_every_art_color_is_used_by_a_builtin_palette` fails if a new `art.*` color appears unused.

## Video overlay mode

Passing a video file instead of an audio file (detected purely by extension — `video.is_video_file`) routes `cli.py`'s `render_cmd` to `run_overlay` instead of `run_render`. It reuses every other stage unchanged, but three things differ:

- **`video.py`** is the only module that touches the source video directly: `probe()` shells out to `ffprobe` for width/height/frame rate (kept as an exact `Fraction`-derived rational string, e.g. `"30000/1001"`, not a rounded float, so a GoPro's non-integer NTSC rate doesn't drift against 30s of audio); `extract_audio()` demuxes the audio track to a temp WAV via ffmpeg before analysis runs (librosa's own MP4 support is a deprecated `audioread` fallback that emits a `FutureWarning` and is slated for removal — not worth depending on); `decode_frames()` pipes the video's frames out of a second ffmpeg subprocess as raw RGB24, trusting that the caller matched `n_frames`/fps to what `probe()` reported rather than re-deriving it; `composite_over()` does premultiplied-alpha "over" compositing (`fg_premultiplied + bg * (1 - alpha)`) of one rendered viz frame onto one decoded video frame.
- **`render.py`** grew an optional `width`/`height`/`transparent_background` path on `render_frame` (default args preserve the old square-opaque behavior exactly, so audio-only mode and all its tests are untouched). When `transparent_background=True`, `draw_frame` skips painting the opaque background, and `surface_to_rgba_premultiplied` reads Cairo's ARGB32 surface out *without* un-premultiplying it — premultiplied "over" compositing needs no divide step, which is simpler and avoids the precision loss un-premultiplying would cost at anti-aliased edge pixels. The shape geometry itself (`deformed_polygon_points`/`scaled_polygon_points`) took an `offset` keyword so the same `size`-based vertex math can be centered within a wider non-square canvas — `render_frame` computes that offset from `(width, height)` vs. `min(width, height)`, so the shape's proportions never stretch to fill a landscape frame, only its position shifts. `Layout.grid` needed no overlay-specific handling to reach parity here — `_layout_instances` only ever consumes the canvas's own `(width, height)`, so a landscape overlay canvas gets four quadrant-fit copies exactly the way a square standalone canvas does.
- Grain and vignette (`postprocess.py`) run unchanged on the RGB channels in both modes — untouched by the alpha channel. Vignette is a pure multiply so it's naturally inert at alpha=0 (transparent corners stay untouched). Grain is additive and is *not* clamped to alpha — this is deliberate, confirmed against a real render: it gives the whole composited frame one continuous grain texture instead of an abrupt dropoff in texture right at the shape's silhouette, at the cost of grain being visible everywhere in the frame, not just on the shape.

`interactive.py` (zero-args mode) is audio-only and was deliberately left untouched — overlay mode is CLI-argument-only for now. Its shape prompt is generated from the `Shape` enum, using each shape's nltl-values description.

## Image Subjects

`--image PATH` replaces the Shape with a user picture (see ADR 0004 and `CONTEXT.md`'s Subject/Image). `cli.resolve_subject` turns `--shape`/`--image` into the one Subject — `--shape` defaults to `None` in Typer purely so passing both can be detected and rejected; `None` then means `face`. The Subject is deliberately not a Preset/YAML field and not offered in interactive mode.

- **`image.py`** owns loading: Pillow (any format), `ImageOps.exif_transpose`, first frame only, converted to RGBA. `Image.premultiplied(w, h)`/`Image.surface(w, h)` hand out LANCZOS-resampled, premultiplied copies at the exact contain-box size, `lru_cache`d — a render only ever needs one or two sizes (single, or grid's quadrant size), so the per-frame cost is never a full-resolution resample.
- **`render.py`** — `image_box` contains the Image (aspect preserved) inside the same bounding square `_polygon_vertices` would use at that Motion's `half_fraction`, so Preset amplitudes mean the same for either Subject. `draw_image_instance` is the Image counterpart of `draw_shape_instance`/`draw_split_instance`: the Image's own pixels replace `outline_color`; `rigid`/`pulse`/`split` are plain Cairo transforms of the cached surface (scale about center / `paint_with_alpha` / midline clip + translate). `rigid`'s inner flash is the flash color painted through the Image's alpha (`mask_surface`).
- **`deform` for Images** (`deformed_image`) uses the contain-box rectangle as the perimeter: `_rect_perimeter_t` gives the arc-length t (top-left start, clockwise — same convention as a Shape's first vertex) where a pixel's ray from the center meets the edge, and the scale is `1 + deform_amplitude * band(t)`. Since that warp is purely radial, it inverts exactly: each output pixel samples the source at `c + (q - c) / scale` (`_sample_bilinear`, on premultiplied values so edges don't fringe). Don't "upgrade" this to a triangle mesh — it'd add seams for no gain. The flash is drawn **on top** with `OPERATOR_ADD`, masked by the warped Image's alpha, because an opaque Image would hide a flash drawn behind it the way a Shape's hollow outline doesn't.
- Overlay mode needs nothing extra: the Image's alpha flows through the same premultiplied RGBA path a Shape's does.
