## Architecture

The pipeline deliberately keeps ffmpeg dumb — no filter graphs, just raw frames piped to its stdin for encoding, and (in overlay mode, see below) raw frames piped from its stdout for decoding — audio analysis and rendering are done entirely in Python so they aren't constrained by what an ffmpeg filter graph can express:

1. **`audio.py`** decodes the full track with librosa up front and produces per-*video*-frame arrays (not per-audio-sample): smoothed log-spaced band energies, a smoothed overall-loudness (RMS) envelope for `Motion.rigid`/`Motion.pulse`, a precomputed flash brightness envelope (onset detection, decayed and combined via elementwise `max` so overlapping onsets don't blow out to solid white), and a precomputed flash color per frame (spectral centroid lerped between two configured hex colors). `hop_length` is chosen as `sample_rate / fps` specifically so analysis-frame indices align 1:1 with output video frames with no resampling step. The RMS envelope is log-compressed with `20*log10` (amplitude-domain), not the `10*log10` used for the power-domain band energies, then percentile-normalized the same way — different compression constant, same normalization pattern.
2. **`render.py`** draws each frame in Cairo, along two independent axes:
   - **`Shape`** (`--shape` flag, default `face`): `face` (an arbitrary quadrilateral, not a square) or `space` (the same bounding square minus the face — a concave pentagon sharing the face's diagonal and short vertical edge as its own boundary, so the two are exact complements). Both the shape's motion and the flash's position scale from the polygon's own centroid (shoelace formula, works for either shape regardless of convexity), not canvas center.
   - **`Motion`** comes from the resolved `Preset`'s `motion` field (see ADR 0002) — there is no `--motion` flag. `deform` (the default) distorts the perimeter per-band (arc-length-parametrized, so control points map to real distance traveled around the boundary regardless of how uneven the edges are — `deform_amplitude`), stroked outline, gradient-blob flash. `rigid` keeps the shape's plain proportions and instead uniformly scales the whole thing from its centroid, driven by the RMS envelope oscillating both directions around baseline (`scale_amplitude`, `scaled_polygon_points`) — solid flat fill instead of a stroke, and the flash becomes a smaller solid-filled concentric copy of the same shape (`draw_inner_shape`) rather than a radial gradient. `pulse` (see ADR 0001) is a constant-size, constant-shape, single-flat-color fill with no flash and no bass/treble centroid color at all — reactivity is entirely the fill's alpha, `preset.pulse_max_opacity * scale_envelope[i]`. `pulse` is also the only motion that inscribes the shape edge-to-edge in the frame's shorter dimension (`_PULSE_HALF_FRACTION = 0.5`, via `pulse_polygon_points`) rather than `deform`/`rigid`'s small centered `_BASE_HALF_FRACTION = 0.35` — `_polygon_vertices` takes an explicit `half_fraction` specifically so this doesn't leak into the other two. `deform_amplitude`/`scale_amplitude`/`pulse_max_opacity` are deliberately separate preset fields (not one field reinterpreted by mode) so a preset's numbers don't silently change meaning depending on an unrelated flag — and since `motion` itself is now also a preset field, each preset's amplitude numbers and its motion are pinned together permanently, not combined at the CLI. Neither shape nor motion special-cases `space`'s concave reflex vertex — if a preset's amplitude ever produces visible self-intersection near that corner, that's the first place to look.
3. **`postprocess.py`** applies grain and vignette as plain numpy ops on the rendered RGB buffer.
4. **`encode.py`** pipes frames to ffmpeg's stdin as raw RGB24 and drives a determinate Rich progress bar (frame count is known up front, unlike nltl-clip which can't observe ffmpeg's internal progress). `render_video` itself is decoupled from how the ffmpeg command is built — callers pass a prebuilt `cmd`, either `build_ffmpeg_cmd` (audio-only: audio file muxed in, re-encoded to AAC) or `build_overlay_ffmpeg_cmd` (overlay mode: the source video's audio track stream-copied through unchanged, since it's the same bytes already used for analysis — no reason to pay for a second lossy encode).
5. **`cli.py`** has a non-obvious Click/Typer detail: `nltl-viz <audio>` (a bare positional argument) and `nltl-viz presets` (an explicit subcommand) must coexist. A plain Typer callback can't do this — Click's group-level argument parsing consumes a leading positional token before ever checking subcommand names. The fix is a custom `_DefaultCommandGroup(TyperGroup)` that overrides `resolve_command` to prepend the hidden `render` command when the first token isn't a known subcommand, combined with `context_settings={"ignore_unknown_options": True}` so the group's own parser doesn't reject subcommand-specific flags like `--preset` before dispatch happens. If you touch the CLI's argument/subcommand structure, re-verify all three invocation shapes (bare filename, flags-first, zero-args interactive, explicit `presets`) — each one broke independently while this was first built.

Presets follow the same shape as nltl-clip's: a flat dataclass of numeric fields, a small hardcoded built-in dict, and an optional YAML config file whose entries are checked first and fall back to the built-ins by name. `config.load()` additionally validates a YAML preset's `motion` field is one of `Motion`'s values (`deform`/`rigid`/`pulse`) at load time, same eagerness as its unknown-field check.

## Video overlay mode

Passing a video file instead of an audio file (detected purely by extension — `video.is_video_file`) routes `cli.py`'s `render_cmd` to `run_overlay` instead of `run_render`. It reuses every other stage unchanged, but three things differ:

- **`video.py`** is the only module that touches the source video directly: `probe()` shells out to `ffprobe` for width/height/frame rate (kept as an exact `Fraction`-derived rational string, e.g. `"30000/1001"`, not a rounded float, so a GoPro's non-integer NTSC rate doesn't drift against 30s of audio); `extract_audio()` demuxes the audio track to a temp WAV via ffmpeg before analysis runs (librosa's own MP4 support is a deprecated `audioread` fallback that emits a `FutureWarning` and is slated for removal — not worth depending on); `decode_frames()` pipes the video's frames out of a second ffmpeg subprocess as raw RGB24, trusting that the caller matched `n_frames`/fps to what `probe()` reported rather than re-deriving it; `composite_over()` does premultiplied-alpha "over" compositing (`fg_premultiplied + bg * (1 - alpha)`) of one rendered viz frame onto one decoded video frame.
- **`render.py`** grew an optional `width`/`height`/`transparent_background` path on `render_frame` (default args preserve the old square-opaque behavior exactly, so audio-only mode and all its tests are untouched). When `transparent_background=True`, `draw_frame` skips painting the opaque background, and `surface_to_rgba_premultiplied` reads Cairo's ARGB32 surface out *without* un-premultiplying it — premultiplied "over" compositing needs no divide step, which is simpler and avoids the precision loss un-premultiplying would cost at anti-aliased edge pixels. The shape geometry itself (`deformed_polygon_points`/`scaled_polygon_points`) took an `offset` keyword so the same `size`-based vertex math can be centered within a wider non-square canvas — `render_frame` computes that offset from `(width, height)` vs. `min(width, height)`, so the shape's proportions never stretch to fill a landscape frame, only its position shifts.
- Grain and vignette (`postprocess.py`) run unchanged on the RGB channels in both modes — untouched by the alpha channel. Vignette is a pure multiply so it's naturally inert at alpha=0 (transparent corners stay untouched). Grain is additive and is *not* clamped to alpha — this is deliberate, confirmed against a real render: it gives the whole composited frame one continuous grain texture instead of an abrupt dropoff in texture right at the shape's silhouette, at the cost of grain being visible everywhere in the frame, not just on the shape.

`interactive.py` (zero-args mode) is audio-only and was deliberately left untouched — overlay mode is CLI-argument-only for now.
